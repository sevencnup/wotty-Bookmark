# 分类管理页面加载性能诊断

## 目标

区分分类管理页面加载缓慢来自数据库查询、后端索引组装、网络传输还是前端 React 首屏渲染，并使用本地现有数据建立可重复的性能证据。

## 执行步骤

1. 检查本地 SQLite、XBEL 文件、接口调用链和前端加载生命周期。
2. 对分类索引查询、后端组装热点和响应体规模进行只读基准测量。
3. 启动临时 API 与管理后台，采集浏览器网络请求、首屏渲染和 DOM 规模。
4. 对比数据库、后端和前端各阶段耗时，形成分层结论。
5. 清理临时脚本、浏览器会话和调试进程，记录诊断结果与验证限制。

## 约束

- 不修改业务逻辑，不修改用户书签和数据库内容。
- 临时测量脚本不得保留在仓库。
- 启动的临时服务和浏览器必须在诊断结束后关闭。

## 验收标准

- 明确区分数据库、后端组装、网络传输和前端渲染的主要耗时层。
- 给出当前数据规模下的可复核测量结果或明确说明运行环境阻塞。
- 不遗留调试日志、临时脚本、测试进程或未授权代码修改。

## 诊断结果

- 已确认分类管理首屏通过 `/api/v1/bookmarks` 读取完整书签树，并在成功后额外读取加密状态。开发模式下根组件启用 React `StrictMode`，分类页加载 effect 没有请求去重。
- API 查询会全量读取当前用户的 `bookmark_nodes`，随后在 Rust 内存中生成文件夹路径、排序书签、递归统计文件夹后代书签数量，并读取 `bookmarks.xbel` 判断状态。
- 数据库存在按用户、父节点、位置排序的索引，但查询不是分页查询；因此数据库读取、后端组装和响应传输都会随节点数量增长。当前代码没有证据表明 SQLite 查询单独是主要瓶颈。
- 前端会同时挂载所有展开分组的书签行、完整组织树和树连接 SVG。现有历史基线在约 1017 条书签、249 个分组、274 个组织树节点时，曾测得分组交互 688～1316ms，优化后为 19～53ms，主因已定位为 React 重渲染。
- 本轮发现本地 SQLite 和 XBEL 测试数据存在；但 Windows 执行器多次无法创建 Python、API 和前端子进程，实时 SQL 毫秒值、HTTP 响应耗时和浏览器 Performance 时间线未能取得，不能伪造这些数值。

## 结论

分类管理页面加载慢是后端全量索引组装与前端全量渲染叠加问题，不是单纯数据库慢。

- 如果主要表现为接口长时间不返回，应继续优化后端全量组装，优先消除每个文件夹反复扫描节点的统计方式，并考虑缓存或预计算路径与计数。
- 如果接口已返回但页面仍迟迟显示或交互卡顿，应继续优化前端首屏，优先虚拟化书签行、减少初始展开数量，并避免组织树连线测量阻塞首帧。
- 如果只在开发环境明显变慢，应先处理 `StrictMode` 下的重复加载请求，或在加载层增加请求去重/取消。

## 验证结果

- Rust 书签模块测试：7 项通过。
- 临时测量脚本已删除。
- 本轮未修改业务代码、数据库或用户书签数据。
